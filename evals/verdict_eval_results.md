# Verdict eval: Agent Proceed verifying agent

Generated by `npm run eval:verdict` (`scripts/run-verdict-eval.ts`) from `evals/verdict_cases.json`. Do not edit by hand: rerun the eval.

## Method

- **Labeled cases (15).** Each case is one agent order at Northwind Outfitters, built from the live catalog (9 products): what the shopper specified, what the agent actually ordered, and the expected verdict, labeled from the rules before running. 5 should Pass; 10 are bad orders (6 Review Required, 4 Hold for Suspicion).
- **Labeling rules.** Only consumer-specified parameters count; an unspecified field is skipped, never a mismatch. Budget (order total), merchant and returns are decision-grade: a mismatch that is not clearly fraud is Review Required. Clearly wrong or suspicious orders (far over budget, wrong category, unknown merchant, a record that does not verify) are Hold for Suspicion.
- **System under test.** The real auditor, unchanged: `runAuditor` → `auditInputFromRecords` → `audit` (`supabase/functions/auditor/`). Each case's session, grant, proposal and checkout action are chained with the product's `appendChained` in an in-memory database, and the auditor seals its receipt into that chain. Returns wording is read by the auditor's own rules reader (`createSparkReader(null)`, keyword rules, no model call), so runs are deterministic. The production Muse Spark reader is not exercised here.
- **Receipt integrity.** Each order's full chain (grant, proposal, action and the sealed receipt) is checked with the product's `verifyOrderChain`: every hash recomputed from the record's fields, every link checked.
- **Baseline.** No verification: every order gets Pass and no receipt is sealed.
- **Metrics.** Miss rate = bad orders that got Pass ÷ bad orders. False-hold rate = good orders that got Review Required or Hold ÷ good orders. Accuracy = correct verdicts ÷ cases. Chargebacks prevented = bad orders that got Review Required or Hold ÷ bad orders (caught before shipping). Receipt integrity = cases whose chain verifies ÷ cases.

## Findings

3 case(s) returned a verdict different from the label. These are reported as returned; the verdict logic was not changed.

- **H1**: expected Hold for Suspicion, got **Review Required**. Far over budget: Rossignol Sender Soul skis $749.95 against a $300 budget (2.5x). Auditor flagged: Budget.
- **H2**: expected Hold for Suspicion, got **Review Required**. Wrong category: shopper asked for a snowboard, agent bought Salomon QST 92 skis ($719.95, within the $800 budget). Auditor flagged: Product.
- **H3**: expected Hold for Suspicion, got **Review Required**. Unknown merchant: the Capita board was bought from 'snowdeals-direct.biz', not a merchant the shopper named or Northwind knows. Auditor flagged: Merchant.

Pattern: H1, H2, H3 are suspicious orders that the auditor caught but rated Review Required, not Hold for Suspicion. In `audit()`, Hold for Suspicion means "the record itself is not trusted" (hash failure, missing component, expired grant, unverified agent); a field mismatch of any size (budget, category, merchant) is Review Required. Every one of these orders is still stopped before shipping, so it counts as a chargeback prevented and not as a miss; only the severity differs from the label.

## Not covered

- Multiple items when one was requested: a checkout action records exactly one product, so the order model cannot express it.
- The Muse Spark returns reader (production) and other languages: covered by the unit tests in `src/test/auditor.test.ts`, not by this eval.
- Specified non-decision attributes (colour, size, delivery) that mismatch: their label is ambiguous under the rules above, so no case relies on one. P2 specifies size and delivery and matches both.
